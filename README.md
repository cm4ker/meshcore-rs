# MeshCore на Rust

Прошивка [MeshCore](https://github.com/meshcore-dev/MeshCore), переписанная на Rust: репитер (с room server)
и компаньон (companion radio).
Совместима по эфиру с оригинальной C++ прошивкой (v1.18): тот же формат пакетов, та же
криптография, та же логика маршрутизации.
Проверена в живой сети: компаньон MeshCore v1.18 логинится, получает статус, телеметрию, ACL,
выполняет CLI и TRACE через эту прошивку.

## Поддерживаемые устройства

| Устройство | Крейт | Чип и радио | Экран | Репитер | Компаньон | Связь с приложением | Обновление по воздуху |
|---|---|---|---|---|---|---|---|
| Heltec WiFi LoRa 32 V4 (V4.2, V4.3) | `firmware/models/heltec-v4` | ESP32-S3, SX1262 + FEM (GC1109 / KCT8103L), flash 16 МБ | OLED 128×64 | да: room server, Wi-Fi и MQTT, бридж ESP-NOW, энергосбережение | да | BLE и Wi-Fi (TCP 5000) одновременно, USB | LoRa, Wi-Fi, BLE; два слота, автооткат |
| Heltec WiFi LoRa 32 V3 | тот же, фича `heltec-v3` | ESP32-S3, SX1262 без FEM, flash 8 МБ | OLED 128×64 | да, как V4 | собирается, на плате не проверен | как V4 | как V4, слоты по 3,4 МБ |
| Seeed XIAO ESP32-C6 + Waveshare Core2021-HF | `firmware/models/xiao-c6` | ESP32-C6, Semtech LR2021, flash 4 МБ | нет | нет | да | BLE или Wi-Fi (не вместе; TCP пока ненадёжен), USB | через подключение приложения; два слота по 1,75 МБ, целый образ без сжатия |
| LilyGO T-Echo | `firmware/models/t-echo` | nRF52840, SX1262, QSPI-флешка | e-paper 200×200 | нет | да, с GPS L76K | BLE, USB | через подключение приложения; один слот, без отката; первая прошивка — UF2 |

В выпуске на GitHub у каждой сборки свой файл `<плата>-<роль>-<версия>-r<номер>.mcfw`
(`heltec-v4-repeater`, `heltec-v3-companion`, `xiao-c6-companion`, `t-echo-companion`…), у T-Echo
ещё `.uf2` для загрузчика по USB.

## Возможности

- репитер: flood/direct, TRACE, ACK, multipart, дедупликация, лимиты хопов, детектор петель, бюджет эфира;
- соседи, discover, логин админа/гостя, запросы статуса/телеметрии/соседей/ACL/владельца, CLI по эфиру;
- **регионы / transport codes** (roadmap): `region put|def|load|save|allowf|denyf|default|home|list`;
- **динамический coding rate** (roadmap): `set dyncr on` — для direct-пакетов к соседу CR выбирается
  по SNR линка (4/5 на сильных, 4/8 на слабых); приёмникам ничего настраивать не нужно;
- **обновление по LoRa**: образ передаётся админскими запросами с любого компаньона (`tools/ota-lora`);
  обычно только **дельта** к работающей прошивке (bsdiff + zlib): ~20 КБ и 3 минуты вместо часа;
- **обновление по Wi-Fi**: `start ota` (можно и удалённо по LoRa) поднимает точку доступа
  `MeshCore-OTA-<имя>` (WPA2, пароль = пароль админа) со страницей загрузки `http://192.168.4.1/`;
- **обновление по BLE**: `start ota ble` (тоже можно удалённо) включает BLE на 15 минут с одноразовым
  PIN в ответе; ретрансляция и Wi-Fi/MQTT при этом работают (`tools/ota-app`);
- два слота прошивки и автооткат: новая прошивка стартует «на пробу», и если трижды не дожила до
  проверки (зависания ловит watchdog), нода возвращается на прежнюю;
- **Wi-Fi + MQTT-наблюдатель**, совместимый с MeshCoreTel: пакеты и статус
  (`mqtt.packets`, `mqtt.tx`, `mqtt.raw`) в `meshcore/<IATA>/<ключ>/…` на meshcoretel.ru (TCP), ommesh и
  LetsMesh EU/US (MQTT поверх WebSocket и TLS 1.3 с проверкой цепочки сертификатов, вход по JWT,
  подписанному ключом ноды); время по SNTP;
- **room server** и **несколько виртуальных нод на одном устройстве** (roadmap): `set room on` +
  перезагрузка — рядом с репитером на том же радио поднимается комната со своим ключом, паролями и
  ACL (посты, рассылка участникам с подтверждением, keep-alive, как upstream `simple_room_server`);
  её CLI доступен по эфиру админу комнаты и в консоли как `room <команда>` (`room.post <текст>`);
  радио, часы и регионы общие с репитером;
- **энергосбережение** (`powersaving on`, как upstream на ESP32): между пакетами чип уходит в light
  sleep до ближайшего таймера (не больше 20 с), радио продолжает приём и будит его пакетом. Не спит
  первые 2 минуты после загрузки, кнопки PRG или команды в консоли, при Wi-Fi, открытом BLE-окне,
  идущем обновлении, пакетах в очереди и подключённом USB-хосте; `powersaving stats` — сколько спал;
- **бридж** (upstream `bridge.*`, ESP-NOW; по умолчанию выключен): репитеры на ESP32 пересылают друг
  другу пакеты по ESP-NOW, совместимо с бриджами upstream (тот же формат кадра, секрет по умолчанию
  `LVSITANOS`). Пакет уходит в бридж один раз и не возвращается обратно; пришедший обрабатывается как
  услышанный по LoRa через `bridge.delay` мс. `set bridge.enabled on` (с перезагрузкой),
  `bridge.source tx|rx` (переданные или принятые пакеты), `bridge.channel` (канал Wi-Fi 1–14; при
  подключённом Wi-Fi — канал роутера), `bridge.secret`, `get bridge.type`. Пока бридж включён, нет
  энергосбережения и Wi-Fi-обновления через точку доступа (`start ota ble` работает);
- watchdog, часы переживают перезагрузки и пропадание питания, страницы на OLED (см. ниже),
  CAD перед передачей, сброс AGC, батарея в телеметрии;
- **компаньон** (`companion`, отдельная прошивка): порт upstream `companion_radio`, протокол приложения
  v14 целиком (контакты, личные сообщения с подтверждением, каналы, вход на репитеры и комнаты, статус,
  телеметрия, CLI, трассировка, поиск пути, экспорт/импорт контактов, подпись, очередь сообщений).
  Подключение: BLE (Nordic UART; PIN задаётся из приложения или `set pin`, без него — случайный на
  экране или 123456 на платах без экрана; привязки сохраняются),
  USB-serial и TCP-порт 5000 при настроенном Wi-Fi (`set wifi.ssid`, `set wifi.pwd`). На Heltec V4
  (ESP32-S3) BLE и Wi-Fi работают одновременно; на XIAO C6 Wi-Fi заменяет BLE (в esp-radio для C6
  совместная работа радио пока не доделана), и TCP там пока ненадёжен: первый ответ на новом
  соединении часто теряется (Wi-Fi C6 в esp-radio 1.0.0-beta.1). Ответы уходят в тот канал,
  откуда пришёл запрос, уведомления — во все.
  **Ручной путь туда и обратно** (`set rtpath on`, по умолчанию выключено; пункт roadmap upstream
  «round-trip manual path»): когда приложение задаёт путь к контакту вручную, компаньон перед первым
  прямым пакетом отправляет контакту этот путь в обратном порядке обычным пакетом PATH, и ответы с
  подтверждениями сразу идут обратно напрямую, а не flood. Без этого upstream узнаёт обратный путь
  только после первого подтверждения, пришедшего flood. Узлы на upstream такой PATH понимают; вход на
  репитер исключение (путь от незнакомого клиента он не берёт), путь уходит с первым запросом после входа.
  Свои ключ, контакты и настройки — в отдельном разделе `companion`, данные репитера не трогаются.
  Обновляется через то же подключение (BLE, USB или TCP), см. ниже.
  На T-Echo GPS (L76K) включается с устройства или из приложения (настройка `gps`, по умолчанию
  выключен, как в upstream); пока он включён, позиция узла берётся с него (advert, телеметрия), а
  часы раз в 30 минут сверяются по спутникам;
- **интерфейс на устройстве** (`firmware/ui`, общий для всех плат, на русском): страницы роли и одна
  кнопка, как в upstream (нажатие — дальше, двойное — назад, удержание — действие на странице).
  Раскладка своя у класса экрана, а не у платы: квадратный e-paper 200×200 (T-Echo) и OLED 128×64
  (Heltec). В верхней строке на всех страницах — заголовок, напряжение батареи (в вольтах: процент
  заряда без типа аккумулятора не вычислить) и Bluetooth. Компаньон: новые сообщения, сообщения, кто рядом, радио, Bluetooth (выключается с
  устройства), GPS, advert, выключение; на Heltec без Bluetooth, GPS и выключения. Репитер: паспорт
  (имя, ID как в путях, пресет) и здоровье, QR-код контакта (приложение MeshCore добавляет репитер
  камерой, ссылка `meshcore://contact/add`), соседи с SNR, трафик, радио, питание и сон, сеть (Wi-Fi,
  MQTT), обновление (удержание открывает окно обновления по BLE, PIN на экране), advert по всей сети.
  OLED гаснет через минуту, и нажатие на тёмный экран только будит его; e-paper не гаснет и
  перерисовывается редко. `cargo run -p ui-preview` рисует все страницы во всех классах в
  `target/ui-preview/` и проверяет, что текст не вылезает за экран и не налезает на соседний.

```
  t-echo/               LilyGO T-Echo (nRF52840, embassy-nrf): компаньон; BLE на Nordic SDC
```

## Сборка и прошивка по USB

```powershell
espup install --targets esp32s3      # один раз (на Windows ARM64 — x64-версия под эмуляцией)
. $HOME\export-esp.ps1               # в каждой новой консоли
cd firmware\models\heltec-v4
cargo build --release
espflash flash --erase-parts otadata target\xtensa-esp32s3-none-elf\release\heltec-v4
# или компаньон:
espflash flash --erase-parts otadata target\xtensa-esp32s3-none-elf\release\companion
```

Heltec V3 собирается из того же крейта с фичей `heltec-v3`: FEM нет, флеш 8 МБ (своя разметка
`partitions-v3.csv`, те же разделы, слоты по 3,4 МБ), консоль на UART0 через CP2102 (на Windows нужен
драйвер Silicon Labs CP210x), мощность новой ноды по умолчанию 22 dBm. Прошивка upstream на V3
размечена иначе, поэтому при первой прошивке флеш стирается целиком (сначала снять дамп
`espflash read-flash 0 0x800000`):

```powershell
cargo build --release --features heltec-v3
espflash erase-flash                 # только в первый раз
espflash flash --flash-size 8mb --partition-table partitions-v3.csv --erase-parts otadata target\xtensa-esp32s3-none-elf\release\heltec-v4
```

Образ для обновления по воздуху — тоже с `--flash-size 8mb --partition-table partitions-v3.csv`.

XIAO ESP32-C6 + LR2021 (обычный stable-тулчейн, `rustup target add riscv32imac-unknown-none-elf`):

```powershell
cd firmware\models\xiao-c6
cargo build --release
espflash flash --erase-parts otadata,meshcore,companion target\riscv32imac-unknown-none-elf\release\companion
```

Подключение модуля (вывод XIAO -> GPIO): CLK D8 -> 19, MISO D9 -> 20, MOSI D10 -> 18, CS D3 -> 21,
DIO11 (IRQ) D1 -> 1, RESET D2 -> 2, BUSY D0 -> 0.

LilyGO T-Echo (`rustup target add thumbv7em-none-eabihf`; для привязок к Nordic SDC нужен LLVM под
архитектуру ПК, `LIBCLANG_PATH` — его каталог `bin`):

```powershell
cd firmware\models\t-echo
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"
cargo build --release
python ..\..\..\tools\uf2\elf2uf2.py target\thumbv7em-none-eabihf\release\companion companion.uf2 --bin companion.bin
python ..\..\..\tools\uf2\flash_uf2.py companion.uf2
python ..\..\..\tools\ota-lora\meshcore_ota.py --register --images images companion.bin   # база для дельт
```

Прошивка ставится UF2-файлом через загрузчик Adafruit, с которым плата продаётся (MBR, SoftDevice
и загрузчик не трогаются). Первый раз — двойное нажатие reset (появляется диск `TECHOBOOT`), дальше
`flash_uf2.py` сам перезапускает плату в загрузчик (открытие порта на 1200 бод). Перед первой
прошивкой стоит сохранить с диска `CURRENT.UF2`: это вся текущая прошивка, и тем же способом её
можно вернуть. Ключ, контакты и каналы переносятся через приложение (экспорт и импорт). Данные
лежат на внешней QSPI-флешке, поэтому файловая система прошивки upstream на ней при этом теряется.
BLE-адрес тот же, что у прошивки upstream, но телефону нужно забыть устройство и сопрячься заново
(PIN 123456, если в приложении не задан другой).
Watchdog прошивки (60 с) продолжает идти и в загрузчике, если войти в него из прошивки
(`flash_uf2.py`, 1200 бод): на копирование файла есть минута, иначе плата вернётся в прошивку.

Спящую ноду (`powersaving on`) по USB не прошить: сначала разбудить её кнопкой PRG или выключить
сон удалённо (`powersaving off` по LoRa). `--erase-parts otadata` нужен, чтобы загрузчик стартовал со слота 0. Ключ и настройки лежат в
отдельном разделе `meshcore` и при прошивке не стираются.

## Обновление по воздуху

Образ для обновления: `espflash save-image --chip esp32s3 --flash-size 16mb <elf> firmware.bin`.

**По LoRa**, через компаньон, у которого репитер в контактах и который знает пароль админа:

```
pip install meshcore
cargo build --release -p ota-delta
python tools/ota-lora/meshcore_ota.py --port COM4 --node PKIO --password-file pw.txt firmware.bin
```

Репитер сообщает SHA-256 работающего образа. Если этот образ есть в хранилище
`firmware/models/heltec-v4/images/`, по эфиру уходит только дельта: при SF7/BW62.5 типичное обновление —
~20 КБ, около 3 минут, плюс ~25 секунд на сборку и проверку образа на самом репитере. Каждый
отправленный образ сохраняется в хранилище; прошитый по USB нужно добавить вручную:
`meshcore_ota.py --register firmware.bin`. Если базы нет, уходит весь образ (сжатый, ~700 КБ,
больше часа). Недостающие куски досылаются.

**По BLE**: в консоли или удалённо (`cmd <нода> "start ota ble"`) выполнить `start ota ble`. Ответ —
имя `MeshCore-OTA-<имя>` и одноразовый PIN; BLE работает 15 минут (пока идёт загрузка — дольше),
потом выключается сам. Ретрансляция и Wi-Fi/MQTT не прерываются. Сопрячь ПК или телефон по PIN и:

```
python tools/ota-app/ota_app.py --ble <адрес> firmware.bin
```

Дельта ~50 КБ уходит за ~15 секунд, сборка и проверка образа на репитере — ещё ~30 секунд. Привязки
хранятся в разделе `companion` и общие с прошивкой компаньона на той же плате.

**По Wi-Fi**: в консоли (или удалённо через `cmd <нода> "start ota"`) выполнить `start ota`. Ответ —
адрес страницы и одноразовый код. Без настроенного Wi-Fi нода поднимает точку доступа
`MeshCore-OTA-<имя>` (страница `http://192.168.4.1/`), с подключённым — страницу на своём адресе в
локальной сети. На странице ввести код и выбрать файл, либо
`curl --data-binary @firmware.bin "http://192.168.4.1/update?code=<код>"`. После трёх неверных кодов
загрузка блокируется до следующего `start ota` (он выдаёт новый код). Если за 15 минут ничего не
загрузили, нода перезагружается и страница пропадает.

**Компаньон** обновляется по тому же подключению, что и приложение (те же запросы, что и по LoRa,
эфир не занимается):

```
python tools/ota-app/ota_app.py --port COM4 firmware.bin
python tools/ota-app/ota_app.py --ble D8:E6:C5:14:21:A8 firmware.bin   # после сопряжения (PIN)
python tools/ota-app/ota_app.py --tcp 192.168.1.50:5000 firmware.bin
python tools/ota-app/ota_app.py --port COM4 --info                     # что сейчас работает
```

Куски образа несут CRC-32, испорченные отбрасываются и досылаются: на T-Echo по USB под нагрузкой
изредка теряются пакеты.

`--raw` шлёт целый образ без сжатия: устройство только проверяет его в конце. Это для прошивок
репитера от 24 октября 2026 (с бриджем, до исправления): у них на коммите сжатого обновления
переполнялся стек, и они откатывались на себя.

На T-Echo место только под одну прошивку: образ (`companion.bin` из `elf2uf2.py --bin`) принимается
во внешнюю QSPI-флешку и проверяется там, а при перезагрузке установщик
(`firmware/models/t-echo/installer`, хранится в 0xED000) переносит его во внутреннюю, ~10 секунд. Если в это
время пропадёт питание, при следующем включении он продолжит с того же места. Отката на прошлую
прошивку нет. Образ кончается хвостом с длиной и SHA-256; он прошивается вместе с приложением, и по
нему прошивка узнаёт свой образ — базу для дельты — как после USB, так и после обновления.

Дельты — как по LoRa, хранилище `firmware/models/<плата>/images/` выбирается по модели устройства. Дельта
по BLE — секунды; целый образ — минуты (на время загрузки прошивка просит у телефона/ПК короткий
интервал соединения). На XIAO C6 (слот 1.75 МБ) образ и его сжатая копия в слот вместе не помещаются,
поэтому целый образ уходит без сжатия. Образ для C6:
`espflash save-image --chip esp32c6 --flash-size 4mb <elf> firmware.bin`.

После обновления репитера: `ota info` в консоли показывает слот и статус пробного запуска, `ota rollback` —
вернуться на предыдущую прошивку.

### Подписанные выпуски

Как закреплённый сертификат TLS. Выпуск собирает и подписывает GitHub Actions
(`.github/workflows/release.yml`; на каждый пуш он только гоняет тесты и собирает все платы, выпуск —
запуск вручную с версией: `gh workflow run release.yml -f version=0.5.0`): каждая сборка упаковывается в `.mcfw` —
манифест (плата, роль, номер выпуска, размер и SHA-256 образа), подписи Ed25519 и сам образ
(`crates/meshcore/src/release.rs`). Корневой ключ — секрет `MCFW_ROOT_KEY` в репозитории, его
отпечаток (SHA-256 открытого ключа) лежит в каждом релизе (`root.txt`).

Устройство, у которого закреплён отпечаток, ставит только выпуск, подписанный этим ключом, для своей
платы и роли и не старее своей сборки, кто бы его ни принёс. Без закреплённого отпечатка — как
раньше, любой образ.

```
set ota.root <отпечаток>          # репитер; несколько через запятую, off — снять
get ota.root                      # закреплённые ключи, плата/роль/номер этой сборки
```

На репитере первый отпечаток можно задать и удалённо (админ и так мог поставить любую прошивку), а
сменить или снять закреплённый — только в консоли по USB. На компаньоне это пользовательская
переменная `ota_root` (в приложении — настройки, «custom vars»; `off` — снять).

Обновлять теми же инструментами, только файлом `.mcfw`: сначала уходит конверт (запрос `0xF6`), и
устройство сразу отвечает, примет ли выпуск; дельты работают как раньше. Страница Wi-Fi-обновления
тоже принимает `.mcfw`.

```
python tools/ota-lora/meshcore_ota.py --port COM4 --node PKIO --password-file pw.txt heltec-v4-repeater-0.5.0-r42.mcfw
python tools/ota-app/ota_app.py --port COM4 xiao-c6-companion-0.5.0-r42.mcfw
```

`tools/ota-sign`: `keygen` (новый корневой ключ), `fingerprint`, `bundle`, `sign`, `verify --root
<отпечаток>`, `extract`, `delta`. Номер выпуска сборка берёт из `MCFW_COUNTER` (локальные сборки — 0, поэтому
им годится любой выпуск).

### Компаньон сам берёт обновление у репитера

Расширение этой прошивки, на обоих концах по умолчанию выключено (`crates/meshcore/src/fwshare.rs`).
Компаньон, ни к чему не подключённый, спрашивает у репитера, которого слышит напрямую, есть ли
обновление для его прошивки, и забирает дельту по LoRa кусками в фоне. Репитер берёт дельты с сервера
выпусков (nw.ommesh.ru) по Wi-Fi. Доверять ни репитеру, ни серверу не нужно: компаньон тянет
обновление только с закреплённым корневым ключом и ставит только то, что этот ключ подписал.

Выпуск CI несёт, кроме `.mcfw`, дельты от трёх предыдущих выпусков (`.mcfd`: конверт нового выпуска,
длина и SHA-256 образа, от которого дельта, и сжатый bsdiff-патч; `ota-sign delta` / `verify --base`).

Репитер (нужен Wi-Fi; дельта хранится в хвосте слота работающей прошивки, до 512 КБ):

```
set fw.serve on                   # отдавать обновления соседям (off — нет)
set fw.server nw.ommesh.ru        # сервер выпусков (HTTP, порт 80; можно host:port)
get fw.status                     # что сейчас лежит или почему не скачалось
```

Компаньон — пользовательские переменные в приложении (или страница «Обновление» на T-Echo):

```
ota_root:<отпечаток>              # без закреплённого корня ничего не тянется
fw_pull:on                        # проверять раз в 12 часов, ставить по кнопке; auto — ставить сразу; off
fw_pull:check                     # проверить сейчас
fw_source:<префикс ключа>         # спрашивать этот репитер; auto — лучший из слышимых напрямую
fw_status                         # (только чтение) что происходит
fw_install:1                      # поставить загруженное
```

Запросы — анонимные (`ANON_REQ` с видами `0x1C` FW_QUERY и `0x1D` FW_GET), только напрямую к соседу,
не флудом; репитер отвечает не чаще раза в секунду. Кусок — 156 байт, между кусками компаньон ждёт
~1,2 с, чтобы не занимать эфир. Дельта T-Echo между соседними выпусками обычно в пределах нескольких
килобайт (0.5.0 → 0.5.1: 986 байт), то есть секунды–минуты эфира.

## Wi-Fi и MQTT

```
set wifi.ssid <сеть>
set wifi.pwd <пароль>
set mqtt.iata OMS            # код региона в топиках; UNSET — не публиковать
set mqtt.ommesh on           # meshcoretel включён по умолчанию; ещё letsmesh-eu, letsmesh-us; не больше 3
set mqtt.tx on               # публиковать и свои передачи
get mqtt.status              # wifi:up ntp:up iata:OMS meshcoretel:up ... ommesh:up ...
```

Настройки сети применяются перезагрузкой. При подключённом Wi-Fi `start ota` поднимает страницу
загрузки на адресе ноды в локальной сети вместо точки доступа (загрузка — только с кодом из ответа).

## Перенос существующей ноды (с сохранением ID)

```
cargo run -p provision -- --prv <ключ из get prv.key> --prefs prefs.txt --admin <pubkey> --clock <unix-время> --out part.bin
espflash write-bin 0x400000 part.bin
```

## Проверки

`cargo test -p meshcore`: ключи/подписи/ECDH сверены байт-в-байт с C-библиотекой upstream,
AES/HMAC — по FIPS-197/RFC 4231, регионы — с независимой реализацией; сквозные сценарии
(пересылка, логин, CLI, TRACE, регионы, динамический CR, OTA по LoRa, очередь MQTT) в `tests/network.rs`,
room server (логин, посты, рассылка и ACK, keep-alive, пароль комнаты, соседство с репитером) — в `tests/room.rs`,
компаньон (сообщения напрямую и через репитер, каналы, вход/статус/CLI на репитере, телеметрия, поиск пути,
импорт/экспорт, очередь, CLI и подпись) — в `tests/companion.rs`; дельта-обновление — в тестах `ota.rs`.
Совместимость компаньона с приложениями: `cargo run -p companion-sim`, затем
`python tools/companion-sim/interop.py` (официальная библиотека `meshcore`, 45 проверок).
