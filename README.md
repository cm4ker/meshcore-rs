# MeshCore на Rust

Прошивка [MeshCore](https://github.com/meshcore-dev/MeshCore), переписанная на Rust: репитер (с room server)
и компаньон (companion radio).
Совместима по эфиру с оригинальной C++ прошивкой (v1.18): тот же формат пакетов, та же
криптография, та же логика маршрутизации.
Проверена в живой сети: компаньон MeshCore v1.18 логинится, получает статус, телеметрию, ACL,
выполняет CLI и TRACE через эту прошивку.

|---|---|---|---|---|---|---|---|

| Heltec WiFi LoRa 32 V3 | `firmware/models/heltec/v3` | ESP32-S3, SX1262 без FEM, flash 8 МБ | OLED 128×64 | да, как V4 | собирается, на плате не проверен | как V4 | как V4, слоты по 3,4 МБ |
| Heltec Wireless Paper (V1.1.1, SSD1682) | `firmware/models/heltec/paper` | ESP32-S3, SX1262 без FEM, flash 8 МБ | e-paper 250×122 | да, как V3, без GPS | да | компаньон: BLE и Wi-Fi, USB (CP2102) | как V3; компаньон через подключение приложения проверен на плате |
| Seeed XIAO ESP32-C6 + Waveshare Core2021-HF | `firmware/models/xiao-c6` | ESP32-C6, Semtech LR2021, flash 4 МБ | нет | да: room server, Wi-Fi и MQTT; батарею не меряет | да | BLE или Wi-Fi (не вместе; TCP пока ненадёжен), USB | через подключение приложения; два слота по 1,75 МБ, целый образ без сжатия |

В выпуске на GitHub у каждой сборки свой файл `<плата>-<роль>-<версия>-r<номер>.mcfw`
(`heltec-v4-repeater`, `heltec-v3-companion`, `xiao-c6-repeater`, `t-echo-companion`…), у T-Echo
и Pro Micro ещё `.uf2` для загрузчика по USB (для веб-флешеров есть ещё `promicro-companion.zip`).

## Возможности

- репитер: flood/direct, TRACE, ACK, multipart, дедупликация, лимиты хопов, детектор петель, бюджет эфира;
- соседи, discover, логин админа/гостя, запросы статуса/телеметрии/соседей/ACL/владельца, CLI по эфиру;
  перебор пароля замедлен: после 10 неверных паролей за 10 минут (от кого угодно) пароли до конца этих
  10 минут не сравниваются; метки времени админов хранятся во флеше вместе с ACL, поэтому записанную
  команду (например, `reboot`) нельзя повторить после перезагрузки;
- **регионы / transport codes** (roadmap): `region put|def|load|save|allowf|denyf|default|home|list`;
- **динамический coding rate** (roadmap): `set dyncr on` — для direct-пакетов к соседу CR выбирается
  по SNR линка (4/5 на сильных, 4/8 на слабых); приёмникам ничего настраивать не нужно;
- **обновление по LoRa**: образ передаётся админскими запросами с любого компаньона (`tools/ota-lora`);
  обычно только **дельта** к работающей прошивке (bsdiff + zlib): ~20 КБ и 3 минуты вместо часа.
  По LoRa ставится только подписанный выпуск, поэтому нужен закреплённый корневой ключ (`set fw.root`);
  без него обновление возможно только по BLE, Wi-Fi или USB;
- **обновление по Wi-Fi**: `fw wifi` (или `start ota`, как в upstream; можно и удалённо по LoRa) поднимает точку доступа
  `MeshCore-OTA-<имя>` (WPA2, случайный пароль в ответе команды) со страницей загрузки `http://192.168.4.1/`;
- **обновление по BLE**: `fw ble` (или `start ota ble`; тоже можно удалённо) включает BLE на 15 минут с одноразовым
  PIN в ответе; ретрансляция и Wi-Fi/MQTT при этом работают (`tools/ota-app`);
- два слота прошивки и автооткат: новая прошивка стартует «на пробу», и если трижды не дожила до
  проверки (зависания ловит watchdog), нода возвращается на прежнюю; `fw rollback` — вернуться вручную;
- **обновления сами по себе** (`fw.auto`): с сервера выпусков по Wi-Fi или от соседа по LoRa, на
  репитере и компаньоне одними и теми же командами, где всё стоит — `fw`;
- **Wi-Fi + MQTT-наблюдатель**, совместимый с MeshCoreTel: пакеты и статус
  (`mqtt.packets`, `mqtt.tx`, `mqtt.raw`) в `meshcore/<IATA>/<ключ>/…` на meshcoretel.ru (TCP), ommesh и
  LetsMesh EU/US (MQTT поверх WebSocket и TLS 1.3 с проверкой цепочки сертификатов, вход по JWT,
  подписанному ключом ноды); время по SNTP;
- **room server** и **несколько виртуальных нод на одном устройстве** (roadmap): `set room on` +
  перезагрузка — рядом с репитером на том же радио поднимается комната со своим ключом, паролями и
  ACL (посты, рассылка участникам с подтверждением, keep-alive, как upstream `simple_room_server`);
  её CLI доступен по эфиру админу комнаты и в консоли как `room <команда>` (`room.post <текст>`);
  радио, часы и регионы общие с репитером;
- **энергосбережение** (`powersaving on`, как upstream на ESP32): между пакетами чип уходит в light
  sleep до ближайшего таймера (не больше 20 с), радио продолжает приём и будит его пакетом. Не спит
  первые 2 минуты после загрузки, кнопки PRG или команды в консоли, при Wi-Fi, открытом BLE-окне,
  идущем обновлении, пакетах в очереди и подключённом USB-хосте; `powersaving stats` — сколько спал;
- **бридж** (upstream `bridge.*`, ESP-NOW; по умолчанию выключен): репитеры на ESP32 пересылают друг
  другу пакеты по ESP-NOW, совместимо с бриджами upstream (тот же формат кадра, секрет по умолчанию
  `LVSITANOS`). Пакет уходит в бридж один раз и не возвращается обратно; пришедший обрабатывается как
  услышанный по LoRa через `bridge.delay` мс. `set bridge.enabled on` (с перезагрузкой),
  `bridge.source tx|rx` (переданные или принятые пакеты), `bridge.channel` (канал Wi-Fi 1–14; при
  подключённом Wi-Fi — канал роутера), `bridge.secret`, `get bridge.type`. Пока бридж включён, нет
  энергосбережения и Wi-Fi-обновления через точку доступа (`fw ble` работает);
- **датчики на I2C** в телеметрии (CayenneLPP, каждый на своём канале): на Pro Micro встроены
  INA219, BME280 и BMP280, а линейные регистровые доставляются текстом без пересборки
  (`sensor add`, см. «Датчики»);
- watchdog, часы переживают перезагрузки и пропадание питания, страницы на OLED (см. ниже),
  CAD перед передачей, сброс AGC, батарея в телеметрии;
- **компаньон** (`companion`, отдельная прошивка): порт upstream `companion_radio`, протокол приложения
  v14 целиком (контакты, личные сообщения с подтверждением, каналы, вход на репитеры и комнаты, статус,
  телеметрия, CLI, трассировка, поиск пути, экспорт/импорт контактов, подпись, очередь сообщений).
  Подключение: BLE (Nordic UART; PIN задаётся из приложения или `set pin`, без него — случайный на
  экране или 123456 на платах без экрана; привязки сохраняются; после трёх неудачных сопряжений подряд
  следующее ждёт минуту, затем вдвое дольше, до часа, а сопряжённые телефоны подключаются без ожидания),
  USB-serial и TCP-порт 5000 при настроенном Wi-Fi (`set wifi.ssid`, `set wifi.pwd`). На Heltec V4
  (ESP32-S3) BLE и Wi-Fi работают одновременно; на XIAO C6 Wi-Fi заменяет BLE (в esp-radio для C6
  совместная работа радио пока не доделана), и TCP там пока ненадёжен: первый ответ на новом
  соединении часто теряется (Wi-Fi C6 в esp-radio 1.0.0-beta.1). Ответы уходят в тот канал,
  откуда пришёл запрос, уведомления — во все.
  **Ручной путь туда и обратно** (`set rtpath on`, по умолчанию выключено; пункт roadmap upstream
  «round-trip manual path»): когда приложение задаёт путь к контакту вручную, компаньон перед первым
  прямым пакетом отправляет контакту этот путь в обратном порядке обычным пакетом PATH, и ответы с
  подтверждениями сразу идут обратно напрямую, а не flood. Без этого upstream узнаёт обратный путь
  только после первого подтверждения, пришедшего flood. Узлы на upstream такой PATH понимают; вход на
  репитер исключение (путь от незнакомого клиента он не берёт), путь уходит с первым запросом после входа.
  Свои ключ, контакты и настройки — в отдельном разделе `companion`, данные репитера не трогаются.
  Обновляется через то же подключение (BLE, USB или TCP), см. ниже.
  На T-Echo GPS (L76K) включается с устройства или из приложения (настройка `gps`, по умолчанию
  выключен, как в upstream); пока он включён, позиция узла берётся с него (advert, телеметрия), а
  часы раз в 30 минут сверяются по спутникам;
- **интерфейс на устройстве** (`firmware/ui`, общий для всех плат, на русском): страницы роли и одна
  кнопка, как в upstream (нажатие — дальше, двойное — назад, удержание — действие на странице).
  Раскладка своя у класса экрана, а не у платы: квадратный e-paper 200×200 (T-Echo), широкий
  e-paper 250×122 (Wireless Paper) и OLED 128×64 (Heltec). В верхней строке на всех страницах — заголовок, напряжение батареи (в вольтах: процент
  заряда без типа аккумулятора не вычислить) и Bluetooth. Компаньон: новые сообщения, сообщения, кто рядом, радио, Bluetooth (выключается с
  устройства), GPS, обновление (что с ним и удержание — проверить или поставить), advert, выключение;
  на Heltec без страниц Bluetooth и выключения. Удержание на главной странице выключает и
  компаньон, и репитер (как кнопка репитера в upstream); включает снова та же кнопка. Репитер: паспорт
  (имя, ID как в путях, пресет) и здоровье, QR-код контакта (приложение MeshCore добавляет репитер
  камерой, ссылка `meshcore://contact/add`), соседи с SNR, трафик, радио, питание и сон, сеть (Wi-Fi,
  MQTT), прошивка (что с обновлением; удержание открывает окно обновления по BLE, PIN на экране),
  advert по всей сети.
  OLED гаснет через минуту, и нажатие на тёмный экран только будит его; e-paper не гаснет и
  перерисовывается редко. `cargo run -p ui-preview` рисует все страницы во всех классах в
  `target/ui-preview/` и проверяет, что текст не вылезает за экран и не налезает на соседний.

```

  packet.rs crypto.rs   формат пакета; AES-128-ECB + HMAC-SHA256 (2 байта MAC)
  identity.rs           Ed25519 (формат ключей orlp/ed25519), ECDH через X25519
  mesh.rs               порт Dispatcher + Mesh
  repeater.rs           порт simple_repeater + CommonCLI
  repeater/room.rs      порт simple_room_server (режим той же ноды)
  companion.rs          порт companion_radio + BaseChatMesh: контакты, каналы, кадры приложения
  region.rs             регионы и transport codes
  ota.rs                сессия обновления (куски в любом порядке, zlib, дельта, проверка SHA-256 и образа ESP)
  uplink.rs             JSON/топики MeshCoreTel, JWT, кодек MQTT 3.1.1, кадры WebSocket
  radio.rs prefs.rs     параметры LoRa и время в эфире; настройки узла
firmware/common/        ESP32 (esp-hal 1.2, ESP32-S3 и ESP32-C6): прерывание радио, разделы flash,
                        слоты и откат, watchdog, Wi-Fi и SNTP, BLE (trouble-host 0.7), USB-JTAG
firmware/fw-core/       общее для любых чипов (embassy, embedded-hal, embedded-storage)
  radio.rs              интерфейс LoRa-трансивера
  sx1262.rs lr2021.rs   драйверы SX1262 и LR2021
  storage.rs            хранилище во flash (+ кольцевой журнал контактов)
  companion.rs          основной цикл компаньона: платформа (`Platform`) и плата (`Board`) снаружи
  frames.rs links.rs    кадры приложения между транспортами и циклом; TCP-сервер
firmware/ui/            интерфейс на устройстве: модель страниц по ролям, кнопка -> намерения, раскладки
                        по классам экранов (embedded-graphics, шрифты U8g2), когда перерисовывать
firmware/vendor/        пропатченные копии trouble-host и embassy-nrf (что и зачем — vendor/README.md)
firmware/models/        платы, у каждой свой крейт: прошивки, разметка flash, тулчейн
  heltec/               Heltec V3 и V4: один workspace, общие Cargo.lock и target
    shared/             общее у V3 и V4: репитер и компаньон вокруг платы, OLED, батарея, GPS,
                        консоль; чем платы различаются, спрашивает через трейт `Variant`
    v4/                 V4: FEM GC1109/KCT8103L (V4.2/V4.3), консоль на USB чипа, flash 16 МБ;
                        образы heltec-v4-repeater, heltec-v4-companion
    v3/                 V3: без FEM, консоль на UART0 (CP2102), flash 8 МБ;
                        образы heltec-v3-repeater, heltec-v3-companion
    paper/              Wireless Paper: V3 с e-paper 250×122 вместо OLED и своими выводами;
                        образы heltec-paper-repeater, heltec-paper-companion
  xiao-c6/              XIAO ESP32-C6 + LR2021 (Waveshare Core2021-HF): компаньон и репитер
                        (`repeater`, на общем `repeater_app`; в выпуски пока не входит)
  t-echo/               LilyGO T-Echo (nRF52840, embassy-nrf): компаньон; BLE на Nordic SDC
                        (trouble-host 0.8), хранилище на QSPI-флешке, экран e-paper;
    installer/          установщик обновления (переносит образ с QSPI во внутреннюю flash)
  promicro/             nRF52840 Pro Micro + SX1262 (embassy-nrf): репитер и компаньон; консоль на USB,
                        настройки во внутренней flash (0xDA000..0xEA000); датчики на I2C
                        (SDA P1.04, SCL P0.11) в телеметрии (INA219/BME280/BMP280 и текстовые дескрипторы, см. «Датчики»);
                        компаньон: BLE на SoftDevice S140 загрузчика, данные в 0x7B000..0xD6000

tools/uf2/              ELF -> UF2 и прошивка платы с UF2-загрузчиком (T-Echo, Pro Micro)

tools/ota-lora/         обновление репитера по LoRa через компаньон (Python, библиотека meshcore)
tools/ota-app/          обновление компаньона по его подключению: BLE, USB или TCP
tools/ota-delta/        дельта-патч для обновления по LoRa (bsdiff)
tools/companion-sim/    сеть на ПК: компаньоны по TCP + репитер; interop.py гоняет её официальной
                        Python-библиотекой meshcore (meshcore-cli тоже подключается)
tools/ui-preview/       все страницы интерфейса во всех классах экранов в PNG + проверка раскладок
```

## Сборка и прошивка по USB

```powershell
espup install --targets esp32s3      # один раз (на Windows ARM64 — x64-версия под эмуляцией)
. $HOME\export-esp.ps1               # в каждой новой консоли
cd firmware\models\heltec
cargo build --release                # все четыре образа, V3 и V4
espflash flash --partition-table v4\partitions.csv --erase-parts otadata target\xtensa-esp32s3-none-elf\release\heltec-v4-repeater
# или компаньон:
espflash flash --partition-table v4\partitions.csv --erase-parts otadata target\xtensa-esp32s3-none-elf\release\heltec-v4-companion
```

Одну плату собирает `cargo build --release -p heltec-v4` (или `-p heltec-v3`), а
`cargo run --release --bin heltec-v4-repeater`, запущенный из `v4\` (или `v3\`), сразу прошивает с
разметкой этой платы.

Heltec V3: FEM нет, флеш 8 МБ (своя разметка `v3\partitions.csv`, те же разделы, слоты по 3,4 МБ), консоль на UART0 через CP2102 (на Windows нужен
драйвер Silicon Labs CP210x), мощность новой ноды по умолчанию 22 dBm. Прошивка upstream на V3
размечена иначе, поэтому при первой прошивке флеш стирается целиком (сначала снять дамп
`espflash read-flash 0 0x800000`):

```powershell
espflash erase-flash                 # только в первый раз
espflash flash --flash-size 8mb --partition-table v3\partitions.csv --erase-parts otadata target\xtensa-esp32s3-none-elf\release\heltec-v3-repeater
```

Образ для обновления по воздуху — тоже с `--flash-size 8mb --partition-table v3\partitions.csv`.

XIAO ESP32-C6 + LR2021 (обычный stable-тулчейн, `rustup target add riscv32imac-unknown-none-elf`):

```powershell
cd firmware\models\xiao-c6
cargo build --release
espflash flash --erase-parts otadata,meshcore,companion target\riscv32imac-unknown-none-elf\release\companion
```

Репитер — тот же `cargo build --release`, прошивается файл `release\repeater`. В выпусках его нет, поэтому
сам он не обновляется: новая версия — своей сборкой (по USB, Wi-Fi или BLE, как у компаньона).

Подключение модуля (вывод XIAO -> GPIO): CLK D8 -> 19, MISO D9 -> 20, MOSI D10 -> 18, CS D3 -> 21,
DIO11 (IRQ) D1 -> 1, RESET D2 -> 2, BUSY D0 -> 0.

LilyGO T-Echo (`rustup target add thumbv7em-none-eabihf`; для привязок к Nordic SDC нужен LLVM под
архитектуру ПК, `LIBCLANG_PATH` — его каталог `bin`):

```powershell
cd firmware\models\t-echo
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"
cargo build --release
python ..\..\..\tools\uf2\elf2uf2.py target\thumbv7em-none-eabihf\release\companion companion.uf2 --bin companion.bin
python ..\..\..\tools\uf2\flash_uf2.py companion.uf2
python ..\..\..\tools\ota-lora\meshcore_ota.py --register --images images companion.bin   # база для дельт
```

Прошивка ставится UF2-файлом через загрузчик Adafruit, с которым плата продаётся (MBR, SoftDevice
и загрузчик не трогаются). Первый раз — двойное нажатие reset (появляется диск `TECHOBOOT`), дальше
`flash_uf2.py` сам перезапускает плату в загрузчик (открытие порта на 1200 бод). Перед первой
прошивкой стоит сохранить с диска `CURRENT.UF2`: это вся текущая прошивка, и тем же способом её
можно вернуть. Ключ, контакты и каналы переносятся через приложение (экспорт и импорт). Данные
лежат на внешней QSPI-флешке, поэтому файловая система прошивки upstream на ней при этом теряется.
BLE-адрес тот же, что у прошивки upstream, но телефону нужно забыть устройство и сопрячься заново
(PIN — случайный, на экране, если в приложении не задан постоянный).
Watchdog прошивки (60 с) продолжает идти и в загрузчике, если войти в него из прошивки
(`flash_uf2.py`, 1200 бод): на копирование файла есть минута, иначе плата вернётся в прошивку.

nRF52840 Pro Micro (репитер, пины как у upstream `variants/promicro`):

```powershell
cd firmware\models\promicro
cargo build --release
python ..\..\..\tools\uf2\elf2uf2.py target\thumbv7em-none-eabihf\release\repeater repeater.uf2
python ..\..\..\tools\uf2\flash_uf2.py repeater.uf2 --drive PROMICRO --vid 0x239A --pid 0x00B3
```

Первый раз — двойное нажатие RST (диск `PROMICRO`): прошивка upstream на касание 1200 бод уходит в
serial DFU, а не в UF2. Дальше `flash_uf2.py` перезапускает плату в загрузчик сам. Узел, который
переезжает с upstream, сохраняет ключ и настройки так: `get prv.key` (только по USB) в файл,
`tools/provision` собирает из него и настроек область данных, `elf2uf2.py ... --data
node.bin@0xDA000` кладёт её в тот же UF2. Загрузчик берёт блоки только ниже 0xEA000: UF2 с блоком
выше не завершается, и до сброса загрузчик не примет и следующий файл. Файловую систему upstream
(0xED000..0xF4000, в ней пароль админа и ACL) прошивка не трогает; в `CURRENT.UF2` её нет.

Обновления по LoRa Pro Micro принимает во внутреннюю flash: приложение до 340 КБ (0x26000..0x7B000),
принятый образ в 0x7B000..0xD6000 (выше до 0xD8000 — датчики `sensor add`), после проверки установщик (0xEA000) переносит его на место и при
потере питания начинает перенос заново. Целый образ со сжатием туда не помещается, поэтому по
эфиру идут дельты; база — образ, который на узле стоит (`meshcore_ota.py --register --images
firmware\models\promicro\images` для прошитого по USB). По LoRa принимается только релиз,
подписанный закреплённым root (`set fw.root` по USB), как на других платах:

```powershell
python tools\ota-lora\meshcore_ota.py --ble D8:E6:C5:14:21:A8 --node <ключ> --password-file pw.txt --images firmware\models\promicro\images release.mcfw
```

По BLE быстрее: `fw ble` (в консоли или удалённо по LoRa) открывает окно обновления на 15 минут,
как на Heltec: имя `MeshCore-OTA-<имя>`, одноразовый PIN в ответе, ретрансляция не прерывается.
BLE даёт SoftDevice S140 6.1.1, который загрузчик держит во flash ниже приложения: он работает
только пока окно открыто (тогда у него радио BLE, часы, flash и RAM ниже 0x20004000); загрузчик с
другим SoftDevice окна не даст (`fw ble` ответит, что его нет). Сопряжение — LE Secure Connections
по PIN; пары живут до перезагрузки, после неё старую пару в Windows надо удалить, а `--pin` удаляет
и сопрягает заново сам:

```powershell
python tools\ota-app\ota_app.py --ble <адрес> --pin <PIN> release.mcfw
```

Компаньон для Pro Micro (`companion`) — тот же цикл, что на T-Echo: приложение по BLE (имя
`MeshCore-<имя>`, PIN 123456, пока в приложении не задан другой) или по USB. BLE даёт тот же
SoftDevice S140, но работает он всё время: через него идут запись во flash, ГСЧ и события VBUS для
USB. Пары с телефонами хранятся во flash (до 4), телефон со случайным адресом узнаётся по его IRK.
Контакты (до 350), каналы и ключ компаньона лежат в 0x7B000..0xD1000, где репитер принимает
обновления: отдельного слота под обновление во flash не остаётся. Поэтому компаньон отдаёт эту
область обновлению на время: когда обновление начинает приходить (от репитера по LoRa, как
`fw.auto` на других платах, или через подключение приложения, `ota_app.py`), ключ, настройки,
каналы, пары, список контактов и 20 последних адвертов переезжают в запасное место
(0xD1000..0xD6000 и 0xED000..0xF4000, где были файлы upstream, 48 КБ), а после установки и
пробного запуска (2 минуты) возвращаются на место. Если обновление брошено или не прижилось, они
тоже возвращаются. Пока данные в запасе, изменения пишутся туда же, пока есть место; список
контактов, который туда не влез, останется таким, каким был при переезде. Адверты контактов
(для «поделиться» и экспорта) компаньон хранит в кольце, как upstream — последние (не меньше 63),
а не все. Сборки до #90 раскладывали область иначе: при первом старте новой данные переезжают
сами. При первом старте на чистой области всё, что было в ней (откатная копия репитера, файлы
upstream), стирается (~8 с). Данные репитера (0xDA000..0xEA000) и датчики (0xD6000..0xD8000)
компаньон не трогает: при возврате на репитер его ключ и настройки на месте, а компаньон при первом
старте берёт из них настройки радио. Ключ у компаньона свой. Залитый через .zip (serial DFU)
обновляется по воздуху так же: загрузчик 0.9.2-OTAFIX CRC прошивки не записывает. Загрузчик, который
его запишет, обновление уже не запустит: тогда `fw` ответит, что слота нет, и обновлять — файлом .uf2.

```powershell
cd firmware\models\promicro
cargo build --release
python ..\..\..\tools\uf2\elf2uf2.py target\thumbv7em-none-eabihf\release\companion companion.uf2
python ..\..\..\tools\uf2\flash_uf2.py companion.uf2 --drive PROMICRO --vid 0x239A --pid 0x00B3
```

Веб-флешеры (кастомная прошивка) берут `promicro-companion.zip` из выпуска: тот же образ, пакетом
для serial DFU загрузчика, как у upstream (`elf2uf2.py --dfu-zip`). Загрузчик 0.9.2-OTAFIX пишет его
на место прошивки: контакты и ключ репитера целы, CRC в настройках загрузчика остаётся нулевым (так на
Wan10, и с `--singlebank`, и без). DFU по BLE из nRF Connect не проверялся: в двух банках он положил бы
образ с 0x89800, поверх контактов. Обновлять компаньон — по воздуху, файлом .uf2 или тем же .zip.
Репитеру пакета нет: его прошивают файлом .uf2.

Спящую ноду (`powersaving on`) по USB не прошить: сначала разбудить её кнопкой PRG или выключить
сон удалённо (`powersaving off` по LoRa). `--erase-parts otadata` нужен, чтобы загрузчик стартовал со слота 0. Ключ и настройки лежат в
отдельном разделе `meshcore` и при прошивке не стираются.

## Обновление по воздуху

Образ для обновления: `espflash save-image --chip esp32s3 --flash-size 16mb <elf> firmware.bin`.

**По LoRa**, через компаньон, у которого репитер в контактах и который знает пароль админа:

```
pip install meshcore
cargo build --release -p ota-delta
python tools/ota-lora/meshcore_ota.py --port COM4 --node PKIO --password-file pw.txt firmware.bin
```

Репитер сообщает SHA-256 работающего образа. Если этот образ есть в хранилище
`firmware/models/heltec/images/`, по эфиру уходит только дельта: при SF7/BW62.5 типичное обновление —
~20 КБ, около 3 минут, плюс ~25 секунд на сборку и проверку образа на самом репитере. Каждый
отправленный образ сохраняется в хранилище; прошитый по USB нужно добавить вручную:
`meshcore_ota.py --register firmware.bin`. Если базы нет, уходит весь образ (сжатый, ~700 КБ,
больше часа). Недостающие куски досылаются.

**По BLE**: в консоли или удалённо (`cmd <нода> "fw ble"`) выполнить `fw ble` (или `start ota ble`). Ответ —
имя `MeshCore-OTA-<имя>` и одноразовый PIN; BLE работает 15 минут (пока идёт загрузка — дольше),
потом выключается сам. Ретрансляция и Wi-Fi/MQTT не прерываются. Сопрячь ПК или телефон по PIN и:

```
python tools/ota-app/ota_app.py --ble <адрес> firmware.bin
```

Дельта ~50 КБ уходит за ~15 секунд, сборка и проверка образа на репитере — ещё ~30 секунд. Привязки
хранятся в разделе `companion` и общие с прошивкой компаньона на той же плате.

**По Wi-Fi**: в консоли (или удалённо через `cmd <нода> "fw wifi"`) выполнить `fw wifi` (или `start ota`). Ответ —
адрес страницы и одноразовый код. Без настроенного Wi-Fi нода поднимает точку доступа
`MeshCore-OTA-<имя>` (страница `http://192.168.4.1/`) с паролем из того же ответа: он случайный и
один до перезагрузки, а не пароль админа. С подключённым Wi-Fi нода поднимает страницу на своём адресе
в локальной сети. На странице ввести код и выбрать файл, либо
`curl --data-binary @firmware.bin "http://192.168.4.1/update?code=<код>"`. После трёх неверных кодов
загрузка блокируется до следующего `fw wifi` (он выдаёт новый код). Если за 15 минут ничего не
загрузили, нода перезагружается и страница пропадает.

**Компаньон** обновляется по тому же подключению, что и приложение (те же запросы, что и по LoRa,
эфир не занимается):

```
python tools/ota-app/ota_app.py --port COM4 firmware.bin
python tools/ota-app/ota_app.py --ble D8:E6:C5:14:21:A8 firmware.bin   # после сопряжения (PIN)
python tools/ota-app/ota_app.py --tcp 192.168.1.50:5000 firmware.bin
python tools/ota-app/ota_app.py --port COM4 --info                     # что сейчас работает
```

Куски образа несут CRC-32, испорченные отбрасываются и досылаются: на T-Echo по USB под нагрузкой
изредка теряются пакеты.

`--raw` шлёт целый образ без сжатия: устройство только проверяет его в конце. Это для прошивок
репитера от 24 октября 2026 (с бриджем, до исправления): у них на коммите сжатого обновления
переполнялся стек, и они откатывались на себя.

На T-Echo место только под одну прошивку: образ (`companion.bin` из `elf2uf2.py --bin`) принимается
во внешнюю QSPI-флешку и проверяется там, а при перезагрузке установщик
(`firmware/models/t-echo/installer`, хранится в 0xED000) переносит его во внутреннюю, ~10 секунд. Если в это
время пропадёт питание, при следующем включении он продолжит с того же места. Отката на прошлую
прошивку нет. Образ кончается хвостом с длиной и SHA-256; он прошивается вместе с приложением, и по
нему прошивка узнаёт свой образ — базу для дельты — как после USB, так и после обновления.

Дельты — как по LoRa, хранилище `firmware/models/<плата>/images/` выбирается по модели устройства. Дельта
по BLE — секунды; целый образ — минуты (на время загрузки прошивка просит у телефона/ПК короткий
интервал соединения). На XIAO C6 (слот 1.75 МБ) образ и его сжатая копия в слот вместе не помещаются,
поэтому целый образ уходит без сжатия. Образ для C6:
`espflash save-image --chip esp32c6 --flash-size 4mb <elf> firmware.bin`.

После обновления: `fw` показывает пробный запуск и через сколько прошивка останется, `fw rollback` —
вернуться на предыдущую (на репитере и по LoRa, админом). Откаченный выпуск узел сам больше не ставит.

### Подписанные выпуски

Как закреплённый сертификат TLS. Выпуск собирает и подписывает GitHub Actions
(`.github/workflows/release.yml`; на каждый пуш он только гоняет тесты и собирает все платы, выпуск —
запуск вручную с версией: `gh workflow run release.yml -f version=0.5.0`): каждая сборка упаковывается в `.mcfw` —
манифест (плата, роль, номер выпуска, размер и SHA-256 образа), подписи Ed25519 и сам образ
(`crates/meshcore/src/release.rs`). Корневой ключ — секрет `MCFW_ROOT_KEY` в репозитории, его
отпечаток (SHA-256 открытого ключа) лежит в каждом релизе (`root.txt`).

Выпуск несёт только платы и роли, код которых изменился: остальные не обновляются зря. CI собирает
каждый образ ещё раз без номера и версии выпуска и с постоянной датой (`MCFW_COUNTER=0`,
`MCFW_VERSION=`, `SOURCE_DATE_EPOCH=0`); хеш такой сборки меняется только с кодом. Хеши всех плат и ролей лежат в
релизе (`content.txt`), и следующий выпуск пропускает те, что совпали с выпуском, за которым он идёт:
у стабильного — с последним стабильным, у dev — с последним любым. Если не изменилось ничего, выпуска
нет.

Устройство, у которого закреплён отпечаток, ставит только выпуск, подписанный этим ключом, для своей
платы и роли и не старее своей сборки, кто бы его ни принёс. Без закреплённого отпечатка оно берёт
любой образ, но только «вблизи»: по BLE после сопряжения, по Wi-Fi через `fw wifi` и по USB. По LoRa
(где хватает пароля админа) и по TCP-порту компаньона (без аутентификации, как в upstream) такое
устройство обновление не начинает. Сборки CI закрепляют корень проекта сразу (`MCFW_ROOT` при сборке):
он действует на новом устройстве и после сброса настроек, а уже сохранённые настройки не меняются.
Локальные сборки корень не закрепляют.

```
set fw.root <отпечаток>           # несколько через запятую, off — снять
get fw.root                       # закреплённые ключи, плата/роль/номер этой сборки
```

На репитере первый отпечаток можно задать и удалённо (админ и так может открыть окно обновления по BLE), а
сменить или снять закреплённый — только в консоли по USB. На компаньоне те же команды работают в CLI
приложения (`meshcore-cli ... cli "set fw.root <отпечаток>"`), а ещё это пользовательская переменная
`fw_root` (в приложении — настройки, «custom vars»; `off` — снять). Удалённый CLI от контакта ключи
компаньона не меняет: без корня компаньон не берёт прошивку по сети, а с корнем берёт её у репитера.

Кто хочет сам решать, какие выпуски ставить на свои устройства, а не брать каждый, закрепляет ещё и
свой ключ владельца. Тогда устройство ставит выпуск, только если его подписали и корень, и владелец.
Ключ создаётся и выпуски подписываются на странице выпусков (nw.ommesh.ru/releases.html): подпись
считает браузер, ключ (файл с 32-байтным seed в hex, как у `ota-sign keygen`) на сервер не уходит.
Можно и у себя: `ota-sign sign <файл>.mcfw --key owner.key`, затем загрузить файл на ту же страницу
(с него берутся только подписи). Сервер раздаёт выпуск с подписью владельца того устройства, которое
спрашивает, поэтому подписи других владельцев обновление не увеличивают.

```
set fw.owner <отпечаток>          # нужен закреплённый корень; несколько через запятую, off — снять
get fw.owner
fw_owner:<отпечаток>              # компаньон, пользовательская переменная (или те же команды в CLI)
```

Правило то же, что у корня: первый ключ владельца можно задать удалённо, сменить или снять — только по
USB. Обновления сами по себе (`fw.auto`) спрашивают сервер только о выпусках, которые
подписал первый закреплённый ключ владельца; пока он не подписал новый выпуск, устройство остаётся на
своей сборке.

Обновлять теми же инструментами, только файлом `.mcfw`: сначала уходит конверт (запрос `0xF6`), и
устройство сразу отвечает, примет ли выпуск; дельты работают как раньше. Страница Wi-Fi-обновления
тоже принимает `.mcfw`.

```
python tools/ota-lora/meshcore_ota.py --port COM4 --node PKIO --password-file pw.txt heltec-v4-repeater-0.5.0-r42.mcfw
python tools/ota-app/ota_app.py --port COM4 xiao-c6-companion-0.5.0-r42.mcfw
```

`tools/ota-sign`: `keygen` (новый ключ: корневой или владельца), `fingerprint`, `bundle`, `sign`,
`verify --root <отпечаток> [--owner <отпечаток>]`, `extract`, `delta`. Номер выпуска сборка берёт из `MCFW_COUNTER` (локальные сборки — 0, поэтому
им годится любой выпуск).

### Обновления сами по себе

Расширение этой прошивки, по умолчанию выключено (`crates/meshcore/src/fwshare.rs`). Репитер берёт
дельты с сервера выпусков (nw.ommesh.ru) по Wi-Fi, ставит себе и отдаёт соседям; репитер без
интернета и компаньон, ни к чему не подключённый, забирают дельту у соседнего репитера по LoRa кусками
в фоне. Доверять ни репитеру, ни серверу не нужно: узел тянет обновление только с закреплённым
корневым ключом и ставит только то, что этот ключ подписал.

Выпуск CI несёт, кроме `.mcfw`, дельты от трёх предыдущих выпусков этой платы и роли (`.mcfd`: конверт нового выпуска,
длина и SHA-256 образа, от которого дельта, и сжатый bsdiff-патч; `ota-sign delta` / `verify --base`).

Команды одни и те же на репитере (консоль по USB или админ по LoRa) и компаньоне (CLI приложения,
`meshcore-cli ... cli <команда>`, удалённый CLI от разрешённого контакта). В приложении у компаньона
это пользовательские переменные: то же имя с `_` вместо точки, действия — `fw_do`.

```
fw                                # что стоит, канал, режим; что происходит и что дальше
fw check                          # проверить сейчас и скачать (fw_do:check)
fw update                         # проверить, скачать и сразу поставить (fw_do:update)
fw install                        # поставить скачанное (fw_do:install)
fw rollback                       # вернуться на прошлую прошивку (fw_do:rollback)
set fw.auto off|download|install  # сам: ничего / скачивать / скачивать и ставить (fw_auto)
set fw.channel stable|dev         # (fw_channel)
set fw.source auto|<имя>|<ключ>   # у кого брать по LoRa; auto — сервер, без него лучший сосед (fw_source)
```

`fw` отвечает двумя строками (у репитера с `fw.serve on` — тремя) и помещается в один ответ по LoRa:

```
0.8.3-dev.1 #45 dev, auto install
downloading 0.8.4 #47 from PKIO: 40 of 64 KB
serves heltec-v4/repeater 0.8.4 #47 (64 KB)
```

Первая строка — выпуск и номер сборки, канал, режим; вторая — что происходит: `next check 04:13`,
`asking nw.ommesh.ru`, `up to date, asked PKIO at 16:13`, `0.8.4 #47 ready (64 KB): fw install`,
`installing 0.8.4 #47: restarting, silent for 1-2 min`, `on trial, kept in 1 min (fw rollback: back to
0.8.3-dev.1 #45)`, `failed: <почему>; next try 17:30`; третья — что лежит для соседей. Те же состояния
по-русски показывают страница «Прошивка» на репитере и «Обновление» на компаньоне (T-Echo, Heltec);
в `fw_status` — вторая строка. Номер выпуска (`0.8.3-dev.1`) сборка берёт из `MCFW_VERSION`.

Только с закреплённым корнем. Первая проверка через 10 минут после загрузки, потом раз в 12 часов
(каждый репитер со своим сдвигом до часа, чтобы сеть не перезагружалась разом), после ошибки — через
час. `download` скачивает и ждёт `fw install`, `install` ставит сам и перезагружается в пробный
запуск: прошивка остаётся, если проработала 2 минуты, а трижды не дожившая откатывается сама.
Откаченный выпуск — сам или `fw rollback` — узел сам больше не ставит; `fw check` и `fw update`
поставят. Включение режима на компаньоне сразу запускает проверку.

Репитер, раздающий обновления (нужен Wi-Fi; дельта хранится в хвосте слота работающей прошивки, до 512 КБ):

```
set fw.serve on                   # отдавать обновления соседям (off — нет)
set fw.server nw.ommesh.ru        # сервер выпусков (HTTP, порт 80; можно host:port)
```

Без связи с сервером (нет Wi-Fi или сервер недоступен) репитер берёт дельту у соседнего репитера по
LoRa, как компаньон: теми же запросами FW_QUERY/FW_GET, напрямую, к соседу с `fw.serve on`. Спрашивает
до четырёх соседей, слышимых напрямую за последние двое суток, лучших по SNR первыми; не ответивший
дважды пропускается. `set fw.source PKIO` (имя соседа из его advert или начало ключа, от 8 hex-цифр)
— только у этого соседа. Кусок — 156 байт, между кусками пауза 3 с: вместе с запросом и ответом это ~4 с на
кусок и около четверти эфира рядом, дельта 40 КБ приходит минут за 20. Ретрансляция при этом идёт как
обычно. Доверять соседу не нужно: ставится только то, что подписал закреплённый корень.

Компаньон спрашивает лучший репитер, который слышит напрямую (или `fw.source`: имя или ключ контакта).
Всё за один заход:

```
meshcore-cli -s COM4 set fw_auto install
meshcore-cli -s COM4 cli "fw"
```

Каналы: выпуск CI собирается как `dev` (по умолчанию, на GitHub — pre-release) или `stable`; канал
записан в подписанном манифесте (флаг `dev`), подделать его нельзя. Устройства по умолчанию следуют
`stable` и сами берут только стабильные выпуски; `set fw.channel dev` — все. Выпуск старее того, что
стоит, узел не ставит: с dev обратно на stable он перейдёт со следующим стабильным выпуском.
Вручную (USB, BLE, приложение, `ota_app.py`) можно поставить любой подписанный выпуск.

Запросы — анонимные (`ANON_REQ` с видами `0x1C` FW_QUERY и `0x1D` FW_GET), только напрямую к соседу,
не флудом; репитер отвечает не чаще раза в секунду. Кусок — 156 байт, между кусками компаньон ждёт
~1,2 с, чтобы не занимать эфир. Дельта T-Echo между соседними выпусками обычно в пределах нескольких
килобайт (0.5.0 → 0.5.1: 986 байт), то есть секунды–минуты эфира.

## Wi-Fi и MQTT

```
set wifi.ssid <сеть>
set wifi.pwd <пароль>
set wifi.enabled off         # выключить Wi-Fi, не забывая сеть; on — включить обратно
set mqtt.iata OMS            # код региона в топиках; UNSET — не публиковать
set mqtt.ommesh on           # meshcoretel включён по умолчанию; ещё letsmesh-eu, letsmesh-us; не больше 3
set mqtt.tx on               # публиковать и свои передачи
get mqtt.status              # wifi:up ntp:up iata:OMS meshcoretel:up ... ommesh:up ...
```

Настройки сети применяются перезагрузкой. При подключённом Wi-Fi `fw wifi` поднимает страницу
загрузки на адресе ноды в локальной сети вместо точки доступа (загрузка — только с кодом из ответа).

## Датчики

Датчики на I2C уходят в телеметрию в формате CayenneLPP, как в upstream: каждый найденный датчик
занимает свой канал, по порядку от 2 (канал 1 — сам узел, напряжение батареи). На Pro Micro шина
I2C на SDA P1.04, SCL P0.11; отсутствующий датчик просто выпадает из телеметрии, застрявшая шина не
держит репитер (таймаут на каждую операцию). Датчик можно либо вкомпилировать (когда нужна
математика компенсации или проверка CRC), либо **доставить текстом без пересборки** (`sensor add`)
— для линейных регистровых.

Встроенные драйверы (Pro Micro): INA219, BME280 и BMP280 — всегда; AHTX0 (AHT10/20), SHTC3 и SHT4X
— за фичей `extra-sensors` (по умолчанию выключена: с ними в 340 КБ приложения остаётся меньше
5 КБ; `cargo build --release --features extra-sensors`). Адреса
датчиков не конфликтуют.

Компаньон Pro Micro отдаёт те же встроенные датчики (и температуру чипа на канале 1): приложению —
всегда, другим — если в его настройках телеметрии разрешено окружение (environment), как в upstream.
Текстовых датчиков у компаньона нет: `sensor add` — команда консоли репитера.

Текстовый датчик описывается одной строкой, хранится во флеше и переживает перезагрузку (до 8 штук):

```
sensor add <имя> <адрес-hex> [init=<рег>:<hex>[,<рег>:<hex>]...] <поле>...
  поле = <lpp>@<рег>:<длина><b|l><s|u>[p][*<множитель>][+<смещение>]
sensor list                       # что добавлено
sensor del <имя>                  # убрать
```

`длина` — 1..4 байта, `b`/`l` — порядок байт (big/little-endian), `s`/`u` — знаковость; из
прочитанного регистра получается `значение * множитель + смещение` (оба необязательны, множитель по
умолчанию 1, смещение 0; отрицательное смещение пишется `+-273.15`). `p` после знаковости означает,
что за данными идёт байт SMBus PEC, и он проверяется (MLX90614 и подобные). `init=` — разовые записи
в регистры после обнаружения датчика (например, калибровка INA226). `lpp` — тип CayenneLPP, один из
`volt cur pow temp hum pres alt`. Все поля одного датчика идут на один его канал.

```
sensor add ina260 41 volt@02:2bu*0.00125 cur@01:2bs*0.00125 pow@03:2bu*0.01
sensor add mlx 5a temp@07:2lup*0.02+-273.15      # объектная T MLX90614, Кельвины -> °C, с PEC
```

Строка разбирается при вводе: `sensor add` отвечает `OK` или `err: <что не так>`, одноимённый датчик
заменяется. Так закрывается весь линейный регистровый хвост (INA-семейство, простые барометры,
MLX90614) без флеша на каждый датчик.

## Перенос существующей ноды (с сохранением ID)

```
cargo run -p provision -- --prv-file key.txt --prefs prefs.txt --admin <pubkey> --clock <unix-время> --out part.bin
espflash write-bin 0x400000 part.bin
```

`key.txt` — ключ из `get prv.key` (128 hex-символов). Файл, а не `--prv <ключ>`: командную строку видят
другие пользователи машины, и она остаётся в истории шелла.
